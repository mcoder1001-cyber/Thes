# T5. Snapshot uniqueness: do copies restored from one image repeat random values and secrets?

## Question
Copies restored from one image start with the same memory. Do they produce the same random
numbers, UUIDs and secrets (Brooker et al., "Restoring uniqueness in MicroVM snapshots")? Do the
snapshot builder's reset hooks fix it?

## Setup
- The Spring Boot function of `../T3-profile/app` with `-Duniq=true`: at start-up it creates a
  `java.util.Random`, a `SecureRandom`, a 16-byte "secret" token from that `SecureRandom`, and
  initialises `Math.random()` and `UUID.randomUUID()`; after the restore point it prints SHA-256
  hashes of: `Random.nextLong()`, `Math.random()`, `UUID.randomUUID()`, 16 `SecureRandom` bytes,
  the token, `System.nanoTime()`. **Only hashes are stored.**
- `-Dreset.hooks=on` registers a CRaC `jdk.crac.Resource` whose `afterRestore` re-seeds the
  `Random`, re-creates the `SecureRandom` and regenerates the token.
- One checkpoint per setting (K = 50, 1 vCPU), 10 restores of each, separate processes, one after
  another. Script: `../T3-profile/t5_rerun.sh` (`grid.py build_uniq uniq`, own cgroup, cores 4–7,
  while the grid ran on 0–3; T5 measures values, not times).
- Three attempts, all raw kept: run 1 (`raw/uniq_run1.jsonl`, the grid's first pass) — hooks off
  fine, hooks-on checkpoint failed (`IllegalAccessException`: `register` looked up on the
  non-exported `ContextWrapper`); run 2 (`../T3-profile/raw/t5_attempt2_proxy_hashcode_NPE/`) —
  the proxy did not answer `hashCode`; run 3 (`raw/uniq_run3.jsonl`, `raw/uniq.csv`) — both fixed,
  the result below.

## Prediction (`prediction.md`)
Hooks off: start-up `Random`, `Math.random()` and token identical in all 10 (1 distinct; the
control). `UUID` and `SecureRandom`: no prediction. `nanoTime` differs. **Hooks on: 10 distinct of
10 for every field.**

## Result (`summary.csv`, distinct values among 10 restored copies)

| field | hooks off | hooks on |
|---|---|---|
| `Random` (made at start-up) `.nextLong()` | **1** | 10 |
| start-up token (from a start-up `SecureRandom`) | **1** | 10 |
| `Math.random()` | **1** | **1** |
| `SecureRandom` (made at start-up), 16 bytes | 10 | 10 |
| `UUID.randomUUID()` | 10 | 10 |
| `System.nanoTime()` | 10 | 10 |

Run 1's hooks-off copies agree with run 3 (same three fields repeat).

## Control
Passed: with hooks off, the start-up `Random` and token are identical in all 10 copies, so the
test sees the problem.

## Verdict
- **Hooks off: confirmed.** Anything derived at start-up and kept in memory is cloned: the
  `Random`'s next value, `Math.random()`'s next value, and a secret generated at start-up — even
  one generated *from* a `SecureRandom` — repeat in every copy.
- **`SecureRandom` and `UUID`** (recorded, not predicted): distinct without hooks. The Zulu CRaC
  JDK re-seeds its secure random sources on restore; the risk is values *already drawn*, not the
  generator.
- **Hooks on: falsified for `Math.random()`.** The hook fixes the `Random` and the token, but
  `Math.random()` keeps repeating: its generator is a private static in `java.lang.Math` with no
  API to re-seed it (reaching it needs `--add-opens java.base/java.lang`).

**Decision** (Stage 5's exit: 10/10 distinct for every field with hooks on): **not met.** The
snapshot builder is not safe for functions that call `Math.random()` (directly or through a
library) before the checkpoint.

## What changes
- The builder needs one of: (a) a reset of `Math`'s generator by reflection with
  `--add-opens java.base/java.lang=ALL-UNNAMED` at checkpoint time, then re-test; (b) a check at
  build time that `Math.random()` was never called before the checkpoint (its holder class not yet
  initialised; `-verbose:class` shows it), refusing the snapshot otherwise; (c) a JDK-side re-seed.
  (b) is the conservative rule; it is one more input to "which stages are safe to snapshot".
- Secrets must be generated after restore or regenerated by a hook; the test shows a hook works
  for objects the function owns.
